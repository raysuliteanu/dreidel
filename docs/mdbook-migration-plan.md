# Plan: Migrate docs to mdBook

## Motivation

The current approach inlines rendered ASCII screenshots directly into
`USER_GUIDE.md`. A test regenerates them and patches the file in-place.
This works, but it means the Markdown source is both documentation and a
generated artefact — the screenshots live in the file they describe.

[mdBook](https://rust-lang.github.io/mdBook/) supports `{{#include path}}`,
which lets the source file reference the screenshot `.txt` files directly
instead of embedding copies. The screenshots are then never stale: every
`mdbook build` picks up whatever the test most recently wrote.

## What changes

| Today | After migration |
|---|---|
| `USER_GUIDE.md` contains inlined screenshots | `src/user-guide.md` uses `{{#include ../docs/screenshots/NAME.txt}}` |
| `patch_user_guide()` rewrites the guide | No patching needed; build reads files directly |
| `verify_user_guide_screenshots` test checks inline content | Test can be removed or kept as a sanity check |
| Docs readable as plain Markdown on GitHub | Rendered HTML via `mdbook build`; GitHub shows raw source |

## Prerequisites

```
cargo install mdbook
```

No other plugins are needed for this use case. Add `mdbook` to the dev-tools
section of `BUILDING.md` once installed.

## Directory layout

```
book/                   # mdBook project root (gitignored build output)
book.toml               # mdBook configuration
src/                    # mdBook source files
  SUMMARY.md            # table of contents — required by mdBook
  index.md              # landing page (thin wrapper or symlink to README.md)
  user-guide.md         # converted from USER_GUIDE.md
  architecture.md       # converted from ARCHITECTURE.md
docs/screenshots/       # unchanged — still generated by cargo test
```

## Migration steps

### 1. Add `book.toml`

```toml
[book]
title = "dreidel"
src = "src"

[output.html]
no-section-label = true
```

### 2. Create `src/SUMMARY.md`

```markdown
# Summary

- [Overview](index.md)
- [User Guide](user-guide.md)
- [Architecture](architecture.md)
```

### 3. Convert `USER_GUIDE.md` → `src/user-guide.md`

Replace each inline screenshot block with an include directive. For example:

**Before:**
```markdown
<!-- screenshot:cpu_compact:begin -->

\`\`\`
┌ [C]PU ...
\`\`\`

<!-- screenshot:cpu_compact:end -->
```

**After:**
```markdown
\`\`\`
{{#include ../docs/screenshots/cpu_compact.txt}}
\`\`\`
```

The `<!-- screenshot:...:begin/end -->` markers and `patch_user_guide()` in
`doc_screenshots.rs` can be removed once all blocks are converted.

Repeat for: `cpu_fullscreen`, `disk_list`, `net_list`, `process_detail`,
`process_list`, `process_tree`, `status_bar`.

### 4. Update `verify_user_guide_screenshots`

The verification test becomes unnecessary because the build renders the
`.txt` files directly. Either remove the test, or repurpose it to assert
that each `.txt` file exists and is non-empty (a lighter check that the
screenshot tests ran).

### 5. Add a CI step

In `.github/workflows/`, add a job (or a step in the existing build job):

```yaml
- name: Build docs
  run: |
    cargo test --test doc_screenshots
    mdbook build
```

Optionally publish the `book/` output to GitHub Pages via `peaceiris/actions-gh-pages`.

### 6. Update links

- `README.md` links to `USER_GUIDE.md` — update to point to the rendered
  book URL or keep pointing at the source file for GitHub readers.
- `AGENTS.md` and `CLAUDE.md` reference `USER_GUIDE.md` by name — update
  to reflect the new path if the file is moved.

## Trade-offs

**Pro:**
- Screenshots are never out of sync with the guide — no patching, no
  verification test needed.
- Rendered HTML is more readable than raw Markdown for end users.
- Standard Rust ecosystem tooling.

**Con:**
- Adds a build step (`mdbook build`) to produce the rendered docs.
- The Markdown source is less readable on GitHub (includes are not rendered
  in the GitHub Markdown viewer).
- `USER_GUIDE.md` at the repo root (which GitHub surfaces automatically)
  would either be removed, become a stub, or diverge from the book source.
  The cleanest fix is a stub that links to the rendered book, but that
  degrades the GitHub reading experience.

## Recommendation

Adopt this migration if rendered HTML docs are a goal (e.g. a public docs
site). If the primary audience reads docs on GitHub or in their editor,
the current `patch_user_guide` approach is simpler and sufficient.
